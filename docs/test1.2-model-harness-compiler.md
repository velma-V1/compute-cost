# Test 1.2 — Model-to-Harness Compiler

## Objective

Test 1.2 is a two-run model onboarding experiment designed to convert a new
local model into a measured, model-specific improvement harness in less than
14 hours of hard wall-clock budget.

It is not a prompt bake-off. It searches the locally testable control surface
of the model + harness system, records where each control helps or hurts, and
compiles those observations into an adaptive deployment policy.

## Hard time contract

| Run | Data partition | Hard ceiling | Active model ceiling |
| --- | --- | ---: | ---: |
| Collection | DISCOVERY | 7h05m | 6h50m |
| Tuning / compile | VALIDATION | 6h15m | 6h |
| Combined | — | **13h20m** | **12h50m** |

TEST2_BLIND and TEST3_PROTECTED are never exposed by either run.

The remaining 40 minutes below the 14-hour user requirement is operational
buffer for setup, model loading, finalization, export, or recovery from a
bounded runtime interruption. Collection received the extra time rather than
removing existing experiments, because per-family frontier/boundary evidence is
a prerequisite for manufacturing useful harness blocks.

## What “full search” means

The set of all possible natural-language prompts is infinite and therefore
cannot be exhaustively enumerated. Test 1.2 instead declares a finite control
grammar and makes that grammar an experimental contract.

Every candidate generated by that declared grammar **must receive minimum
coverage before tuning is allowed to start**.

The collection run may adapt how much replication a candidate receives, but it
may not silently omit a declared candidate.

The tuning run refuses to consume a collection whose
`control-grammar-coverage.json` does not state
`all_declared_candidates_tested=true`.

Capability coverage is not just a raw-score checklist. Before replication depth

The collection emits:

- `capability-family-coverage.json` — proves all 40 families have baseline

- `capability-building-block-manufacturing-map.json` — per family, records

  candidate building blocks for the next manufacturing stage.

The tuning run refuses a collection unless all 40 families are marked
manufacturing-ready. A family with no positive control is still retained: its
harm/null evidence becomes a negative constraint rather than being dropped.

## Stratified open-pool partitioning

The legacy hash split is retained as the authority for protected data.
`TEST2_BLIND` and `TEST3_PROTECTED` fixture IDs are immutable.

For Test 1.2 only, the already-open legacy `DISCOVERY + VALIDATION` pool is
rebalanced by capability family. This prevents random hashing from leaving a
family with too little manufacturing evidence while preserving future blind
audits.

Preflight requires at least:

- 3 DISCOVERY fixtures per required capability family; and
- 1 VALIDATION fixture per required capability family.

If the open pool cannot satisfy that contract, the run fails before model
calls rather than borrowing from a protected partition.

## Value-density contract

Test 1.2 is not allowed to treat score improvement as the only useful result.
Every raw observation is indexed into every applicable value channel, including
baseline/frontier evidence, rescue evidence, pass preservation, hard-case
evidence, compute cost, routing evidence, manufacturing evidence, tuning data,
negative transfer, and pruning evidence.

Every capability family must leave collection with a capability-improvement
dossier covering the critical value dimensions:

- measured raw frontier and difficulty spread;
- seed/repeatability evidence;
- failure-side rescue and pass-side preservation;
- hard-case/frontier-extension probes;
- prompt control;
- reasoning effort;
- generation budget;
- context window;
- compute/temperature routing;
- planning;
- verification;
- retry/recovery;
- state tracking;
- memory;
- context selection/compression;
- tool policy;
- stop/escalate policy;
- latency/token/call efficiency;
- negative-effect search;
- activation boundaries;
- contrastive tuning evidence.

The collection is not manufacturing-ready if a critical value dimension is
missing for any of the 40 capability families.

### Negative results are improvement assets

A harmful result is never discarded merely because it lowers a score. Depending
on its observed boundary, it becomes one or more of:

- a **route veto** preventing a known regression;
- a **conditional gate** showing where a control helps and where it hurts;
- an **activation-boundary sensor**;
- a **regression sentinel** for future harness/model changes;
- a **contrastive tuning negative**;
- a **compensation target** for a later combined block;
- a **latency/token veto** when it adds cost without quality.

A null control is also useful. If it adds calls, tokens, or latency without
quality, it becomes a pruning/cost-avoidance rule.

Avoiding a known harmful or useless controller is counted as real harness
improvement because it preserves the base model's score and compute budget
relative to a naive "apply every good-looking trick" system.

### Required advancement path

For each family, Test 1.2 must identify one or more evidence-backed advancement
paths:

- harness capability lift;
- hard-case/frontier lift;
- reliability lift;
- latency speedup;
- token/call reduction;
- negative-gating score protection;
- frontier-extension target; or
- residual fine-tuning target after cheaper harness owners are exhausted.

A family with no proven positive harness control is **not dropped**. Its null
and harmful evidence constrains the harness, while its recurrent residual
failures become higher-value fine-tuning targets.

## Efficient experimental design

The campaign intentionally does **not** evaluate the full Cartesian product.
That would spend most of the 14-hour budget testing redundant combinations.

Instead:

1. Map raw capability across the DISCOVERY partition.
2. Replicate a balanced failure/pass subset to estimate instability.
3. Use a balanced covering design over prompt placement × representation ×
   dose × recurrence so every level appears for every control primitive.
4. Give every declared control candidate a mandatory breadth trial.
5. Use fractional-factorial / interaction scouting for promising cross-control
   combinations.
6. Recreate exact failures for recovery-policy tests.
7. Use pass sentinels to map negative transfer.
8. Allocate replication depth according to information gain, rescue signal,
   negative-transfer risk, value per call, and family coverage gaps.
9. Preserve every positive, negative, and null control example as tuning data.

The campaign therefore saves calls by reducing redundant replication, **not**
by reducing the breadth of the declared control catalog.

## Real tool boundary

Test 1.2 includes real execution against deterministic in-process synthetic
tools (calculator, typed user lookup, weather lookup, and state read/write).
This measures harness loops, argument validation, dependency sequencing, error
feedback, retry behavior, result use, and state handoff without side effects.

This is **not** claimed to be native provider function calling or access to
external tools. The compiled policy can later be mapped onto MCP/Docker/real
tools while retaining the measured controller rules.

## Tuning / compile run

The second run consumes only a collection that passed complete control
coverage. It uses VALIDATION and performs successive halving:

1. baseline VALIDATION;
2. screen individual high-value controls and compiled routing candidates;
3. halve weak policies;
4. widen validation on survivors;
5. tune routing/boundary behavior;
6. replay residual failures;
7. confirm final candidate(s).

The final artifact is a model-specific adaptive harness policy containing:

- direct/default path;
- routing map;
- activation conditions;
- compute/budget escalation rules;
- validated retry/recovery rules;
- tool execution policy;
- do-not-use / negative-transfer registry;
- cost expectations;
- residual model-owned failures.

## Fine-tuning boundary

Harness tuning and weight tuning are different owners.

The collection corpus intentionally creates material suitable for later
supervised/preference fine-tuning: task text, failed baseline response,
successful treatment response, control identity, failure type, and cost.

The tuning run only recommends weight tuning when a recurrent failure remains
after the compiled harness has already tested the cheaper owners (prompt,
reasoning/compute, verification/retry, context/memory, and tool policy).

This prevents training model weights to compensate for a controller defect.

## Release rule

A new model is not considered harness-compiled if:

- any of the 40 required capability families is missing;
- any capability family lacks its mandatory manufacturing control-surface floor;
- any declared collection candidate was never exercised;
- VALIDATION was used during collection;
- DISCOVERY was used for tuning;
- TEST2_BLIND or TEST3_PROTECTED was exposed;
- the final policy has unbounded negative transfer;
- the compiled harness requires oracle labels unavailable at deployment;
- the collection/tuning evidence cannot be integrity verified.
