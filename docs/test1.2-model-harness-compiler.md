# Test 1.2 — Model-to-Harness Compiler

## Objective

Test 1.2 is a two-run model onboarding experiment designed to convert a new
local model into a measured, model-specific improvement harness in less than
14 hours of hard wall-clock budget.

It is not a prompt bake-off. It searches the locally testable control surface
of the model + harness system, records where each control helps or hurts, and
compiles those observations into an adaptive deployment policy.

## Hard time contract

| Run | Data partition | Hard ceiling | Active model ceiling |
| --- | --- | ---: | ---: |
| Collection | DISCOVERY | 6h15m | 6h |
| Tuning / compile | VALIDATION | 6h15m | 6h |
| Combined | — | **12h30m** | **12h** |

TEST2_BLIND and TEST3_PROTECTED are never exposed by either run.

The remaining 1h30m below the 14-hour user requirement is operational buffer
for setup, model loading, finalization, export, or recovery from a bounded
runtime interruption.

## What “full search” means

The set of all possible natural-language prompts is infinite and therefore
cannot be exhaustively enumerated. Test 1.2 instead declares a finite control
grammar and makes that grammar an experimental contract.

Every candidate generated by that declared grammar **must receive minimum
coverage before tuning is allowed to start**.

The collection run may adapt how much replication a candidate receives, but it
may not silently omit a declared candidate.

The tuning run refuses to consume a collection whose
`control-grammar-coverage.json` does not state
`all_declared_candidates_tested=true`.

## Search surface

The declared improvement surface includes:

- prompt/control primitives;
- system, prefix, middle, suffix, and post-candidate injection placement;
- prose, bullet, and schema representations;
- low/normal/high control dose;
- recurrence counts 1/2/3;
- decomposition and planning;
- pre-answer verification;
- critique and repair;
- failure diagnosis and retry;
- strategy reset;
- minimal repair;
- dynamically synthesized failure-specific corrective injections;
- state tracking;
- evidence ledgers and working memory;
- context selection and compression;
- tool-selection and argument-policy controls;
- deterministic real in-process synthetic tool execution;
- tool error recovery and state handoff;
- specialist delegation;
- skeptical-auditor delegation;
- independent branch + adjudication;
- ensemble/consensus controls;
- A+B+A compositions;
- self-routing;
- risk-gated escalation;
- stop/sufficiency policies;
- reasoning effort;
- generation budget;
- context window;
- temperature;
- seed/instability replication;
- cost-aware selection;
- negative-transfer boundaries;
- model-owned residual / fine-tuning qualification.

## Efficient experimental design

The campaign intentionally does **not** evaluate the full Cartesian product.
That would spend most of the 14-hour budget testing redundant combinations.

Instead:

1. Map raw capability across the DISCOVERY partition.
2. Replicate a balanced failure/pass subset to estimate instability.
3. Use a balanced covering design over prompt placement × representation ×
   dose × recurrence so every level appears for every control primitive.
4. Give every declared control candidate a mandatory breadth trial.
5. Use fractional-factorial / interaction scouting for promising cross-control
   combinations.
6. Recreate exact failures for recovery-policy tests.
7. Use pass sentinels to map negative transfer.
8. Allocate replication depth according to information gain, rescue signal,
   negative-transfer risk, value per call, and family coverage gaps.
9. Preserve every positive, negative, and null control example as tuning data.

The campaign therefore saves calls by reducing redundant replication, **not**
by reducing the breadth of the declared control catalog.

## Collection outputs

The collection run produces, among other evidence:

- complete candidate registry;
- finite control grammar;
- candidate coverage ledger;
- raw capability map;
- reasoning/compute surface;
- controller mechanism map;
- real synthetic tool-execution map;
- retry/recovery map;
- interaction atlas;
- activation boundaries;
- negative-transfer boundaries;
- cost/value frontier;
- residual failure ownership;
- fine-tuning readiness;
- positive/negative/null tuning example corpus;
- preliminary harness-policy blueprint.

The corpus retains the observable task, raw baseline response, treatment
response, treatment identity, activation context, outcome delta, failure class,
and cost. Blind/protected material is never used.

## Real tool boundary

Test 1.2 includes real execution against deterministic in-process synthetic
tools (calculator, typed user lookup, weather lookup, and state read/write).
This measures harness loops, argument validation, dependency sequencing, error
feedback, retry behavior, result use, and state handoff without side effects.

This is **not** claimed to be native provider function calling or access to
external tools. The compiled policy can later be mapped onto MCP/Docker/real
tools while retaining the measured controller rules.

## Tuning / compile run

The second run consumes only a collection that passed complete control
coverage. It uses VALIDATION and performs successive halving:

1. baseline VALIDATION;
2. screen individual high-value controls and compiled routing candidates;
3. halve weak policies;
4. widen validation on survivors;
5. tune routing/boundary behavior;
6. replay residual failures;
7. confirm final candidate(s).

The final artifact is a model-specific adaptive harness policy containing:

- direct/default path;
- routing map;
- activation conditions;
- compute/budget escalation rules;
- validated retry/recovery rules;
- tool execution policy;
- do-not-use / negative-transfer registry;
- cost expectations;
- residual model-owned failures.

## Fine-tuning boundary

Harness tuning and weight tuning are different owners.

The collection corpus intentionally creates material suitable for later
supervised/preference fine-tuning: task text, failed baseline response,
successful treatment response, control identity, failure type, and cost.

The tuning run only recommends weight tuning when a recurrent failure remains
after the compiled harness has already tested the cheaper owners (prompt,
reasoning/compute, verification/retry, context/memory, and tool policy).

This prevents training model weights to compensate for a controller defect.

## Release rule

A new model is not considered harness-compiled if:

- any declared collection candidate was never exercised;
- VALIDATION was used during collection;
- DISCOVERY was used for tuning;
- TEST2_BLIND or TEST3_PROTECTED was exposed;
- the final policy has unbounded negative transfer;
- the compiled harness requires oracle labels unavailable at deployment;
- the collection/tuning evidence cannot be integrity verified.
